# מערכת ניהול לקוחות לכלכלת המשפחה

Next.js + Supabase (Postgres, Auth, Storage) + Prisma. פרויקט נפרד לגמרי מ-עזרי, בעבור ישראל שרמן (מרצה לאוריינות פיננסית + יועץ משכנתאות).

## מה כבר בנוי ונבדק מקצה לקצה (בלייב, לא רק build)

- **Auth לקוח**: כניסה עם קוד חד־פעמי למייל (Supabase Auth, OTP). `src/app/login`
- **Auth יועץ**: אותו מנגנון OTP בדיוק, אבל `Advisor.authUserId` במקום `FamilyMember.authUserId` — מפנה ל-`/admin` במקום `/dashboard`. `src/lib/advisor.ts`
- **DB**: סכמת Prisma מלאה (`prisma/schema.prisma`), מחוברת לפרויקט Supabase אמיתי (`qgexfrmmjrbsnswtmyaf`).
- **מיילים**: SMTP מותאם מול Resend. **שני** תבניות מייל תוקנו להציג קוד גלוי ({{ .Token }}) — גם "אישור הרשמה" וגם "Magic Link or OTP" הנפרדת (משתמשים חוזרים עוברים דרכה, לא דרך הראשונה — קל לפספס).
- **דשבורד תקציב**: קטגוריות, הוצאות, מנגנון קיזוז (reallocation) לפי ה-PRD, הוצאות קבועות/חוזרות עם checkbox. `src/lib/budget.ts`, `src/app/dashboard`
- **שאלון קליטת לקוח**: משוחזר מהטופס האמיתי של ישראל ב-Google Forms (forms.gle/F2XrbsX4uLnZYDGE7), data-driven (`formSchema.ts`), עיצוב מותאם למותג (נווי/זהב/קרם), ללא login, גישה לפי טוקן. `src/app/onboarding/[token]`
- **סיכומי פגישות ללקוח**: מוצגים באזור האישי של הלקוח יחד עם "על מה נתמקד בשלב הבא". `src/lib/meetings.ts`
- **אזור יועץ (`/admin`)**: רשימת משפחות (עם תג "X פגישות" ותג "חוב פתוח") → עמוד משפחה עם מצב תשלום (טוגל), קישור לשאלון קליטה (אם רלוונטי), העלאת מסמכים/הקלטות ל-bucket פרטי ב-Storage עם signed URL, הוספת סיכום פגישה, והוספת משימות. כל הטפסים כפופים ל-`assertFamilyOwnedByAdvisor` (יועץ יכול לגעת רק במשפחות שלו). `src/app/admin`
  - הוספת סיכום פגישה, טוגל מצב תשלום, הוספת משימה — **נבדק בלייב**, עובד.
  - העלאת קובץ — קוד תקין (אותו דפוס storage+signed-url שכבר עובד), **לא נבדק בלייב** כי דפדפן ה-agent לא תמך בהעלאת קובץ אמיתי. צריך בדיקה ידנית חד־פעמית.
- **לידים (`/admin/leads`)**: הוספת ליד ידני, שינוי סטטוס, "המרה למשפחה" (יוצר `Family` חדשה עם `onboardingToken` אקראי ומפנה לעמוד שלה). **נבדק בלייב**, כולל ההפניה אחרי המרה.
- **משימות ללקוח**: היועץ מוסיף משימה (הרגל/חיסכון, עם קישור כלי/סרטון אופציונליים) מעמוד המשפחה; הלקוח רואה אותה ב-`/dashboard` עם כפתור "סמן כהושלם", ופס "התקדמות במשימות" (אחוז השלמה) ליד פס התקציב. `src/lib/tasks.ts`
- **יעד חיסכון משותף**: כרטיס "יעד החיסכון שלנו" בדשבורד הלקוח — מצרף `savingsAmountAnnual` מכל משימות סוג "חיסכון" (יעד = הכל, הושג = מה שסומן כהושלם). מוצג רק אם יש למשפחה משימת חיסכון אחת לפחות. `getFamilySavingsProgress` ב-`src/lib/tasks.ts`. **נבדק בלייב**.
- **מגמה חודש מול חודש**: לכל קטגוריית תקציב בדשבורד הלקוח, השוואה להוצאה באותה קטגוריה בחודש הקודם (▲/▼ בשקלים, או "כמו חודש שעבר"). `getFamilyBudgetSummary` כבר תמך בפרמטר `month` — רק הוספנו קריאה שנייה עם החודש הקודם. **נבדק בלייב**.
- **מסמכים והקלטות ללקוח**: הלקוח רואה עכשיו (לא רק היועץ) את המסמכים שהועלו עבור המשפחה שלו, עם כפתור "פתח" ש-signed URL נוצר לו רק אחרי בדיקת בעלות (`familyId` תואם). `src/lib/documents.ts`, `src/app/dashboard/DocumentRow.tsx`. **נבדק בלייב** (כולל בדיקת ה-ownership check עצמו).
  - כל שלושת הפיצ'רים האלה **נבדקו בלייב במלואם** — כולל דרך `/dashboard` בפועל, לא רק מול ה-DB — כי מצאנו שאפשר להשתמש באותו session מחובר (advisor) כדי לצפות גם ב-`/dashboard`: הרשומה המקורית של `FamilyMember` בזרע כבר חולקת את אותו `authUserId`.
- **מעקב הכנסות**: קטגוריות הכנסה (`IncomeCategory`) + רשומות הכנסה (`Income`) — מודלים מקבילים ל-`BudgetCategory`/`Expense`. `src/lib/income.ts`, `src/app/dashboard/IncomeTools.tsx`. כרטיס "סיכום חודשי" (סה"כ הכנסות / סה"כ הוצאות / נטו) בראש הדשבורד. **הקטגוריות עצמן וכל המבנה נלקחו ישירות מהאקסל האמיתי של ישראל** (קישור בשיחה) — גם קטגוריות ההוצאה בזרע עודכנו להיות זהות לאקסל (אוכל, הוצאות קבועות, ביגוד והנעלה, אוכל בחוץ, דלק רכב קו, פנאי, רכישות קטנות, שונות, מעשרות, החזרי חובות, חיסכון לשנתי) במקום placeholder גנרי. **נבדק בלייב**, כולל הוספת הכנסה בפועל ועדכון הסיכום.
- **קטגוריות חדשות מהלקוח**: עד עכשיו קטגוריות (גם הוצאה וגם הכנסה) נוצרו רק דרך `prisma/seed.ts` — אף אחד לא יכול היה להוסיף אחת. עכשיו יש אופציית "+ קטגוריה חדשה" בשני הטפסים (`ExpenseTools`/`IncomeTools`); הבחירה בה חושפת שדה שם, והקטגוריה נוצרת (או מופעלת מחדש אם הייתה מושבתת) לפני הרישום. מסתנכרן אוטומטית לכל מקום שקורא את הקטגוריות (רשימת התקציב, dropdown הבא, מנגנון הקיזוז) כי זו שורה רגילה ב-DB. **נבדק בלייב** עם הדוגמאות המדויקות שישראל נתן ("הכנסה מטיפולים", "הוצאה על בריאות") — כולל שהקטגוריה החדשה מיד הופיעה גם במודאל הקיזוז כשחרגתי ממנה בכוונה.
- **תזכורות משימות במייל**: `/api/cron/task-reminders` (מופעל ע"י Vercel Cron, `vercel.json`, יומי ב-7:00 UTC) סורק משימות פתוחות עם דדליין בתוך 3 ימים או שכבר עברו, למשפחות עם `portalActive`. שולח מייל אחד לכל בן משפחה עם רשימת המשימות שלו, דרך Resend API (`src/lib/email.ts`, **לא** אותו SMTP שמשמש את Supabase Auth — צריך `RESEND_API_KEY` נפרד, כבר מוגדר ב-`.env.local`). `NotificationLog` מונע שליחה כפולה לאותה משימה תוך 48 שעות. `src/lib/reminders.ts`.
  - **הקישור במייל הוא magic link אמיתי, לא "לך תתחבר"**: לוחצים וזה מכניס ישירות ל-`/dashboard`, בלי קוד. זה עבד ב-flow לא טריוויאלי: ה-token של Supabase חוזר ב-**fragment** של ה-URL (`#access_token=...`), לא ב-query param — כלומר השרת (Route Handler) לעולם לא רואה אותו, רק JavaScript בצד הלקוח. בגלל זה `/auth/confirm` הוא client component (`src/app/auth/confirm/page.tsx`) שקורא את ה-hash בעצמו וקורא ל-`supabase.auth.setSession()`. גיליתי את זה ע"י בדיקה ישירה של ה-redirect בפועל (curl, לא הנחה) — היה קל לפספס ולבנות route handler שרת-צד שפשוט אף פעם לא יעבוד.
  - `/api/cron/task-reminders` נוסף ל-`PUBLIC_PATHS` ב-middleware (מאמת את עצמו עם `CRON_SECRET` בתוך ה-route, לא עם session cookie — זו קריאה שרת-לשרת).
  - **נבדק בלייב מקצה לקצה**: יצרתי משימה עם דדליין קרוב, הרצתי את ה-cron ידנית (`sent:1`), אימתתי שהרצה חוזרת לא שולחת שוב (`sent:0` — ה-cooldown עובד), ואימתתי ש-401 חוזר בלי הסוד הנכון. את ה-token exchange עצמו (magic link → session אמיתי עם access_token+refresh_token) בדקתי ישירות מול Supabase (לא רק קראתי קוד) — **אבל** לא הצלחתי ללחוץ בפועל על הקישור מדפדפן אמיתי (הדפדפן הפנימי שלי חסם ניווט לדומיין של Supabase). **כדאי שישראל יבדוק בעצמו לחיצה אמיתית על הקישור מהמייל שהתקבל בתיבה שלו.**
  - **חשוב**: "אוטומטי" באמת (בלי שמישהו מריץ ידנית) דורש **deploy ל-Vercel** — ה-cron ב-`vercel.json` לא יתחיל לרוץ לבד עד שהאתר יעלה לאוויר שם, וגם צריך להגדיר `RESEND_API_KEY` ו-`CRON_SECRET` כמשתני סביבה בפרויקט ב-Vercel (לא רק ב-`.env.local` המקומי).

- **אזור ניהול תקציב מורחב ללקוח** (בהשראת מיפוי מעמיק של מערכת תקציב אחרת של ישראל, taktziv.0548454392.com — ראה `אפיון-מערכת-ניהול-תקציב.md` בפרויקט עזרי): ישראל ביקש במפורש "ניהול תקציב באותו רעיון" באזור הלקוח. נוספו 4 מסכים חדשים דרך `DashboardNav` (`src/app/dashboard/DashboardNav.tsx`, מוצג גם בראש `/dashboard`):
  - **יומן תנועות** (`/dashboard/transactions`, `src/lib/transactions.ts`) — הצגה, עריכה ומחיקה של כל הכנסה/הוצאה. זה היה הפער הכי גדול לפני התוספת: אפשר היה רק להוסיף ולראות סכום מצטבר, לא לראות/לתקן תנועה בודדת.
  - **דוחות** (`/dashboard/reports`, `src/lib/reports.ts`) — גרף מגמת 6 חודשים (הכנסות/הוצאות/נטו, ספריית `recharts` חדשה) + פירוט לפי קטגוריה לחודש הנוכחי.
  - **תקציב שנתי** (`/dashboard/annual`, `src/lib/annualBudget.ts`) — טבלת 12 חודשים לכל קטגוריית הכנסה/הוצאה, תכנון מול בפועל, עם צביעה אדום/כתום בחריגה. **פשוט מדעת**: "מתוכנן" הוא `plannedAmount` הקבוע של הקטגוריה בכל חודש (אין עדיין יעד חודשי משתנה, ואין את מנגנון "מילוי לפי חציון" שיש ב-taktziv).
  - **מעשרות** (`/dashboard/maaser`, `src/lib/maaser.ts`) — טוגל מעשר (10%) / חומש (20%) שנשמר על `Family.maaserRatePercent` (שדה חדש, מיגרציה `20260928130946_family_maaser_rate`), הכנסה חייבת, חובה, שולם (מזוהה מקטגוריית ההוצאה הקיימת "מעשרות"), נותר, וחוב נגרר מחודשים קודמים. **פשוט מדעת**: "הכנסה חייבת" היא **כל** ההכנסה החודשית — אין עדיין הבחנה בין הכנסה רגילה למתנה/החזר חוב פטור ממעשר כמו ב-taktziv, כי `IncomeCategory` לא מבדיל סוגי הכנסה. אם זה משנה הלכתית לישראל, זו תוספת שדה קטנה.
  - כל הארבעה **נבדקו בלייב** על משפחת הבדיקה מול ה-Supabase האמיתי: הוספת תשלום מעשר בפועל (6,450 ₪ הכנסה → 645 ₪ חובה ב-10%, תשלום 200 ₪ נרשם והתעדכן מיד גם ביומן התנועות), עריכת תנועה, טבלה שנתית עם נתוני ספטמבר האמיתיים. `tsc --noEmit` ו-`eslint` נקיים על כל הקבצים החדשים.
  - שרתי ה-dev הישן (PID קודם) הוחלף כי הוא טען Prisma Client ישן מלפני המיגרציה — אם נתקלים ב-`Unknown field` דומה אחרי `prisma migrate dev`, זה הפתרון (להרוג את התהליך הישן ולהריץ `npm run dev` מחדש, לא מספיק `prisma generate` לבד).

## הערה חשובה על Resend

בלי אימות דומיין משלך, Resend שולח רק לכתובת המייל שאיתה נרשמת ב-Resend. **לפני שלקוחות אמיתיים יכולים להתחבר, צריך לחבר דומיין** (Resend → Domains → Add Domain, ואז כמה רשומות DNS). זה גם ישפר את אמינות המסירה (פחות סיכוי לתיקיית ספאם). ראינו בפועל שמיילים חוזרים ("Magic Link or OTP") לפעמים לא הגיעו ל-Gmail תוך דקות למרות שResend הראה "Delivered" — כנראה reputation issue של הדומיין המשותף של Resend תחת traffic חוזר ומהיר. לא בעיה בקוד.

## מה סוכם ונדחה במפורש (לא לגעת בלי שישראל מעלה מחדש)

- **וואטסאפ**: הושהה לפי בקשה מפורשת ("בא נחכה עם החיבור של הווצאפ").
- **תמלול הקלטה → טיוטת מייל סיכום → אירוע יומן**: ישראל בחר במפורש שעזרי יעשה את זה **ידנית** דרך הג'ימייל/יומן האמיתיים שלו, ולא כפיצ'ר במערכת — ואז חזר בו וביקש שיהיה אפשר **להעלות את ההקלטה עצמה** לתיקיית הלקוח בתוך המערכת (זה מה שנבנה ב-`/admin`). השלב הבא בשרשרת (תמלול אוטומטי + טיוטת מייל + יומן) עדיין לא נבנה ולא סוכם איך בדיוק — צריך להחליט עם ישראל.
- **ציון בריאות פיננסי** (בהשראת "פלוס מינוס"): ישראל ענה **לא** במפורש. לא לבנות בלי שהוא מעלה מחדש.

## הדומיין וה-deploy (עדכון 28.9.2026)

- **`clalatmishpaha.com`** נקנה, אומת ב-Resend (DKIM + CNAME לשליחה + DMARC, הוגדרו ב-Namecheap Advanced DNS). מיילי תזכורת המשימות יוצאים ממנו עכשיו (`src/lib/email.ts`) — יכולים להגיע לכל נמען, לא רק לבעל חשבון ה-Resend.
  - **עדיין לא עודכן**: כתובת השולח של מיילי ה-OTP (קוד ההתחברות) — זו מוגדרת בנפרד ב-Supabase Dashboard (Auth → SMTP Settings), לא בקוד. עד שמישהו יעדכן שם, קודי התחברות עדיין יגיעו רק לבעל חשבון ה-Resend/Supabase.
- **הפרויקט חי ב-Vercel**: `https://family-finance-portal.vercel.app` (production, team `zzz-4ee2`). נמצאו ותוקנו שני באגים אמיתיים שמנעו deploy מוצלח, שני commits נפרדים:
  1. **`CRON_SECRET` עם רווח מיותר** בערך שנשמר ב-Vercel לפני כמה שעות — Vercel דוחה ערכי header עם whitespace, וזה הפיל את ה-build תוך 3 שניות, לפני שאפילו התחיל לקמפל. תוקן ע"י יצירת ערך חדש (בלי whitespace) דרך `vercel env add --sensitive`, בלי לחשוף אותו בשום מקום.
  2. **Prisma Client לא נוצר אף פעם ב-install נקי של Vercel** (`package.json` היה `"build": "next build"` בלבד) — כל קובץ שמייבא מ-`@prisma/client` נכשל עם "has no exported member", כולל שורה ארוכה של שגיאות `implicit any` שהיו רק תוצר לוואי. תוקן ע"י `"build": "prisma generate && next build"`. נבדק מקומית לפני ה-push: מחיקת `node_modules/.prisma` ואז build, כדי לדמות בדיוק install נקי.
  - שני התיקונים אומתו: build עובר נקי מקומית (סימולציה של install נקי) **וגם** ב-Vercel בפועל (`vercel ls` מראה `Ready`, ונבדק ש-`/login` באמת עולה מהאינטרנט, לא רק שה-build עבר).

## המשך מכאן (session חדש)

1. **לעדכן את כתובת השולח של מיילי ה-OTP ב-Supabase Dashboard** (Auth → SMTP Settings) לדומיין המאומת — זה מה שחסם עד עכשיו קודי התחברות ללקוחות אמיתיים, ועדיין חסום.
2. **שני פריטים שלא נבדקו בלחיצה אמיתית מדפדפן (דורשים את ישראל):** (א) העלאת קובץ אמיתי ב-`/admin/families/[id]`, (ב) לחיצה על קישור ה-magic link בפועל ממייל תזכורת משימות אמיתי (המנגנון עצמו אומת בקוד/API, רק לא "מהצד השני" של לחיצה בדפדפן אמיתי) — עכשיו שהדומיין מאומת, שווה לבדוק את זה שוב במייל אמיתי.
3. **מה שהוחלט לא לבנות (במכוון) בממשק הלקוח**: מעקב שווי נקי/השקעות, ציון בריאות פיננסי (נשאל ישראל במפורש, ענה לא), דשבורד עם widgets להתאמה אישית, צ'אט מובנה (יש וואטסאפ לזה, מושהה) — לא מתאים למוצר ליווי תקציב (לא ניהול הון).
4. **"רצף הרגלים"** (streak) על משימות מסוג habit נדחה — דורש להחליט על מנגנון "משימה חוזרת" שעדיין לא קיים בסכמה. לא התחלנו בזה.
5. **תוספות אפשריות לאזור התקציב החדש (לא סוכמו, לשאול את ישראל)**: יעד חודשי משתנה לתקציב השנתי (במקום `plannedAmount` קבוע) + מנגנון "מילוי לפי חציון"; הבחנה בין סוגי הכנסה (רגילה/מתנה/החזר חוב) כדי שההכנסה החייבת במעשר תהיה מדויקת הלכתית.

## סביבת פיתוח

הכל כבר מוגדר ורץ (`.env.local` קיים עם פרטי הפרויקט האמיתי, לא לשתף/להעלות ל-git). כדי להריץ מחדש:

```bash
npm install
npm run dev
```

- מעקב שווי נקי/השקעות, דשבורד ניתן להתאמה אישית — **הוחלט במכוון לא לבנות** (לא מתאים למוצר ליווי תקציב)
